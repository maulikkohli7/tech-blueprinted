The whole tour, step by step

Postgres never reads or changes a page directly on disk. Every page is first copied into shared memory, into a pool of slots called shared buffers. This tour uses just 4 of them.

  1. SELECT * FROM accounts;

    The server has just started, so every buffer is empty. Page 0 wasn't cached, so it was read from disk into buffer 0.

  2. SELECT * FROM accounts;

    Same page, and this time it was already in memory: a cache hit. Its usage count (the dots) went up. Popular pages keep high counts.

  3. UPDATE accounts SET balance = 0 WHERE id = 1;

    The change happened only in memory. Buffer 0 is now dirty: the copy of page 0 on disk is out of date. (A separate log, the WAL, protects the change in case of a crash.)

  4. INSERT INTO accounts VALUES (4, 'dave', 400), (5, 'erin', 500), (6, 'frank', 600), (7, 'grace', 700), (8, 'heidi', 800), (9, 'ivan', 900), (10, 'judy', 1000);

    The table grew by two pages. New pages are created directly in memory, so there was nothing to read. Three buffers are now dirty.

  5. CREATE INDEX ON accounts(id);

    Building an index writes it straight to its file, bypassing the buffers. On disk it exists, but none of its pages are cached yet.

  6. SELECT * FROM accounts WHERE id = 9;

    The index root took the last free buffer. The leaf needed an eviction: the clock hand swept round lowering usage counts until one reached zero, skipping the root it was holding. That victim was dirty, so it was written to disk first. Then the leaf pointed to the very page just evicted, so it was read straight back.

  7. CHECKPOINT;

    A checkpoint writes every dirty buffer to disk. Now evicting any of them costs nothing.

  8. SELECT * FROM accounts;

    Reading 3 pages through 4 buffers: some hits, some reads, some evictions. Real servers have thousands of buffers, and a good one serves 99% of reads from memory.
