Tour 8 of 16, Cleanup

Long transactions

VACUUM can only remove a dead row once no running transaction could still need it. One forgotten transaction can hold back cleanup for the whole database.

The whole tour, step by step

VACUUM can only remove a dead row once no running transaction could still need it. One forgotten transaction can hold back cleanup for the whole database.

  1. -- session B
BEGIN ISOLATION LEVEL REPEATABLE READ;

    B opens a transaction that will stay open for a while.

  2. -- session B
SELECT * FROM accounts;

    B's snapshot is now fixed, and its oldest-needed transaction ID (its xmin) is advertised to everyone.

  3. -- session A
DELETE FROM accounts WHERE id = 2;

    Transaction 101 deleted bob and committed. Any new query will skip him.

  4. -- session A
VACUUM;

    VACUUM kept bob. B's snapshot was taken before 101 committed, so B may still read him. VACUUM's limit, the "removal horizon", is set by the oldest snapshot still open.

  5. -- session B
SELECT * FROM accounts;

    Proof: B still sees bob.

  6. -- session B
COMMIT;

    B finally finishes.

  7. -- session A
VACUUM;

    The horizon moved past 101, so bob is removed. Watch for "idle in transaction" connections in production: they cause exactly this.
