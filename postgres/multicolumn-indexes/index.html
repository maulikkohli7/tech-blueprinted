The whole tour, step by step

One B-tree can cover several columns. It sorts by the first column, then by the second within each value of the first. That order decides which queries it can help.

  1. INSERT INTO accounts VALUES (4, 'alice', 50), (5, 'bob', 75), (6, 'alice', 900), (7, 'carol', 20), (8, 'bob', 400), (9, 'alice', 300), (10, 'dave', 100), (11, 'erin', 700), (12, 'frank', 800);

    People can now hold several accounts: alice has four, bob three.

  2. CREATE INDEX ON accounts(name, balance);

    Entries are sorted by name, and by balance within each name, like a phone book sorted by surname and then first name. All of alice's accounts sit together, smallest balance first.

  3. SELECT * FROM accounts WHERE name = 'alice' AND balance > 200;

    Both conditions steer the search: jump to alice, then to balance > 200 within her entries. Only the 2 matching entries were read.

  4. SELECT * FROM accounts WHERE name = 'bob';

    The first column on its own works too, because all of bob's entries are next to each other.

  5. SELECT * FROM accounts WHERE balance > 500;

    balance on its own can't use this index. High balances are scattered across every name, so the sort order doesn't help, and Postgres falls back to a sequential scan. (Postgres 18 can sometimes "skip scan" such an index when the first column has few distinct values; this lab doesn't model that.)

  6. DROP INDEX accounts_name_balance_idx;

    Now let's build the same index with the columns the other way round.

  7. CREATE INDEX ON accounts(balance, name);

    Sorted by balance first. alice's accounts are now spread across the index.

  8. SELECT * FROM accounts WHERE name = 'alice' AND balance > 200;

    Same answer, more work. Only balance > 200 could steer the search, so Postgres read all 6 entries in that range and checked the name on each one. Rule of thumb: put columns you compare with = first, and a range column (<, >, BETWEEN) last.
