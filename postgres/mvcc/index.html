The whole tour, step by step

Postgres never changes a row in place. Each change writes a new version, stamped with the ID of the transaction that made it. This design is called MVCC, multi-version concurrency control.

  1. SELECT ctid, xmin, xmax, * FROM accounts;

    Every tuple starts with a header. xmin is the ID of the transaction that inserted it, here 100. xmax is the ID of the transaction that deleted it, and 0 means nobody has.

  2. UPDATE accounts SET balance = 150 WHERE id = 1;

    Transaction 101 did two things. It set xmax = 101 on the old alice, and it inserted a new alice with xmin = 101. The old version's t_ctid now points at the new one, (0,4), so Postgres can follow the trail.

  3. SELECT ctid, xmin, xmax, * FROM accounts;

    Only the new alice comes back. The old version is still on the page, but the transaction that replaced it has committed, so every query skips it. Leftover versions like this are what "table bloat" means.

  4. DELETE FROM accounts WHERE id = 3;

    A DELETE doesn't erase anything either. It only sets xmax = 102 on carol.

  5. BEGIN;

    Now an explicit transaction, so we can undo it.

  6. INSERT INTO accounts VALUES (4, 'dave', 400);

    dave was inserted by transaction 103 on a new page. He's amber: written to the page, but his transaction hasn't committed.

  7. ROLLBACK;

    Rolling back doesn't remove dave either. Postgres only records transaction 103 as aborted in its commit log (pg_xact), and from then on every reader treats dave as never inserted.
