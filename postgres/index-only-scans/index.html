If a query only needs columns the index already has, can Postgres skip the table entirely? Sometimes. It needs the visibility map, and an index that holds every column the query asks for.

  1. INSERT INTO accounts VALUES (4, 'dave', 400), (5, 'erin', 500), (6, 'frank', 600), (7, 'grace', 700), (8, 'heidi', 800), (9, 'ivan', 900), (10, 'judy', 1000);

    Ten rows over three pages.

  2. CREATE INDEX ON accounts(id);

    An index on id.

  3. SELECT id FROM accounts WHERE id >= 5;

    Only id is needed, and the index contains it. Yet Postgres still visited the heap for all 6 rows ("Heap Fetches: 6"). The index can't say whether a row is visible to this query, so each one had to be checked in the table.

  4. VACUUM;

    Besides cleaning, VACUUM maintains the visibility map: one bit per page meaning "every row here is visible to every transaction". All three pages are now marked all-visible.

  5. SELECT id FROM accounts WHERE id >= 5;

    Heap Fetches: 0. For each entry Postgres checked the page's bit, found it set, and returned the id straight from the index.

  6. SELECT id, balance FROM accounts WHERE id >= 5;

    Ask for balance as well and it's an ordinary Index Scan again. balance isn't in the index, so every row needs a heap visit, all-visible or not.

  7. DROP INDEX accounts_id_idx;

    Let's replace the index with one that also carries balance.

  8. CREATE INDEX ON accounts(id) INCLUDE (balance);

    INCLUDE stores balance in every leaf entry next to the id. The tree is still sorted and searched by id only; balance just rides along. That makes it a "covering" index for queries that need id and balance.

  9. SELECT id, balance FROM accounts WHERE id >= 5;

    An index-only scan again, with Heap Fetches: 0. Both columns came straight from the index.

  10. UPDATE accounts SET balance = 0 WHERE id = 9;

    The cost: balance is now stored in an index, so changing it can't be a HOT update. The index needed a new entry carrying the new balance, and page 2 lost its all-visible bit.

  11. SELECT id, balance FROM accounts WHERE id >= 5;

    Page 1 still skips the heap; page 2 needs heap fetches again until the next VACUUM. INCLUDE suits columns you read often and change rarely.
