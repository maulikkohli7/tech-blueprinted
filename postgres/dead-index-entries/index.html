The whole tour, step by step

An index entry is just a key and a ctid. It knows nothing about xmin or xmax, so it can't tell live rows from dead ones.

  1. CREATE INDEX ON accounts(id);

    One index on id.

  2. CREATE INDEX ON accounts(balance);

    A second index, on balance.

  3. UPDATE accounts SET balance = 110 WHERE id = 1;

    The new version of alice got an entry in both indexes, even in the id index, although id didn't change. Each index needs to know the new ctid. This is why every extra index slows down writes.

  4. UPDATE accounts SET balance = 120 WHERE id = 1;

    Another update, another entry in each index. Page 0 was full, so Postgres first cleaned it in passing: the oldest alice was removed, leaving a "dead" line pointer that indexes still point at.

  5. SELECT * FROM accounts WHERE id = 1;

    The index has three entries for id 1. Postgres had to follow all three to the heap to find the one live version, because only the heap knows what's alive.

  6. VACUUM;

    VACUUM removed the stale entries from both indexes first, and only then freed the heap slots. Doing it the other way round could leave an index entry pointing at a slot reused by some other row.

  7. SELECT * FROM accounts WHERE id = 1;

    One entry, one heap visit.
