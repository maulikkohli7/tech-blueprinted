Tour 6 of 16, Concurrency

Row locks

Two transactions try to update the same row. Postgres has no separate lock table for rows: the lock is the xmax field you already know.

← → keys work too

The whole tour, step by step

Two transactions try to update the same row. Postgres has no separate lock table for rows: the lock is the xmax field you already know.

  1. -- session A
BEGIN;

    A opened a transaction.

  2. -- session A
UPDATE accounts SET balance = balance - 50 WHERE id = 1;

    A is transaction 101 and set xmax = 101 on alice's current version. While 101 is running, that xmax also works as a lock on the row.

  3. -- session B
UPDATE accounts SET balance = balance - 30 WHERE id = 1;

    B found the same version, saw xmax 101 still running, and has to wait. Real Postgres would pause B here; this lab stops the statement instead.

  4. -- session A
COMMIT;

    A commits; alice is now 50.

  5. -- session B
UPDATE accounts SET balance = balance - 30 WHERE id = 1;

    B now sees A's version (50) and updates that one, to 20. Neither update was lost.

  6. -- session B
BEGIN ISOLATION LEVEL REPEATABLE READ;

    The same race again, this time under REPEATABLE READ.

  7. -- session B
SELECT * FROM accounts WHERE id = 1;

    B's snapshot is fixed with alice at 20.

  8. -- session A
UPDATE accounts SET balance = 0 WHERE id = 1;

    A commits a newer version of alice.

  9. -- session B
UPDATE accounts SET balance = balance + 5 WHERE id = 1;

    B's snapshot still shows alice at 20, but someone B can't see has already replaced that version. Updating it would silently undo A's change, so Postgres refuses with a serialization error.

  10. -- session B
ROLLBACK;

    Apps using REPEATABLE READ are expected to catch this error and retry the whole transaction.
